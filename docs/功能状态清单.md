# Pathleap 功能状态清单

> 本文件是 Pathleap **唯一的功能状态来源**。README、发布说明、界面对照页里出现的「已实现 / 未验证 / 未接入」口径，
> 都要与本文件一致；不一致时以本文件为准，并回改上游文档。
>
> 基线：`1.1.0`（2026-11-14，tag `v1.1.0`，CI run `43514510017`）。
> 设置页每一项都必须能在 §1 找到对应行。

## 0. 状态定义与维护规则

### 0.1 三态

| 状态 | 判定标准 |
| --- | --- |
| **未实现** | 有计划但代码里没有可用实现（无命令、无数据源、或只有被禁用的占位控件） |
| **已实现未验证** | 代码在，但没有可复现的实测证据（截图、采样、日志、自动化用例） |
| **已实现已验证** | 代码在，且附有证据链接（文档章节、截图、采样数据、CI 运行号） |

「部分」不是状态：一个功能如果有可用子集和缺失子集，拆成两行分别定状态（例：更新通道拆成「稳定版」与「预览版」）。

### 0.2 谁在什么时点更新

| 角色 | 时点 | 动作 |
| --- | --- | --- |
| 功能开发者 | 提交功能、降级功能、或改设置页条目的同一个提交内 | 更新对应行的状态与证据；新增「未实现」行时写明阻塞原因 |
| 发版负责人（打 tag 的人） | **创建 tag 之前** | 逐行复核状态与证据，登记 §9「更新记录」（版本、日期、复核人） |
| 发版负责人 | CI 通过之后 | 回填 CI 运行号、Release 资产链接；状态有变化时同步 README 与发布说明 |

未完成上述复核与登记，视为发布流程未完成（见 [发布检查清单](发布检查清单.md) §3）。

### 8.2 「清单漂移」结论

用户的判断成立：**原来确实有清单，但那份清单不是功能台账，做到后面就漏了**。

- 唯一的旧清单是 [界面验收报告](界面验收报告.md) §4「未接入项」，只有 5 条：
  资源管理器显示、`Tab`、目录增删与排除规则、更新镜像、侧栏两页。
- 设置页里实际标注「未接入」的条目有 12 条（A1–A12），旧清单**漏了 7 条**：
  已安装程序、浏览器历史与书签、网络位置、鼠标中键/侧键、更新通道预览版、拖放、`Ctrl+Enter`（旧清单里的
  「在资源管理器中显示」只写了结果行，没覆盖快捷键页那一行）。
- 漏的原因不是「忘了写代码」，而是**流程里从来没有「功能台账」这一环**：
  1. 旧清单是「逐屏对照设计稿」的副产物，只覆盖设计稿画出来、且实现时被显式取舍的项；
     范围页三张卡、更新通道、拖放、鼠标键这些「在页面里但不在主对照行」的项天然进不去。
  2. 降级动作发生在「界面还原」这一个提交里，只有代码注释和界面标签，没有降级记录（谁决定、为什么、何时做）。
  3. 发布检查清单第 36 行只要求「界面已标注 + README 未完成项里列出」，不要求「清单与代码逐项一致」，
     也不要求复核状态变化。README 未完成项是手写的，因此漏了 7 条也照样通过检查。
