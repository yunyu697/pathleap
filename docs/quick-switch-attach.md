# 快速切换栏吸附方案：技术验证与取舍

## 背景

文件对话框打开时，「快速切换栏」需要以附属面板的形态出现：宽度约为对话框的一半、贴在底边、随对话框移动/缩放/最小化，对话框关闭立即消失；多个对话框各有一条、互不串位，只有前台对话框对应的那条响应键盘。

## 候选方案与实测结论

### 方案 A：SetParent 成对话框的子窗口

做法：`SetParent(栏, 对话框)`，再用 `SetWindowPos` 把栏放进对话框客户区底边内侧。

实测结论：

| 项 | 结果 |
| --- | --- |
| 跨进程 SetParent 能否成功 | 能，返回上一个父窗口，无错误 |
| 子窗口是否随对话框移动 | 是（系统原生跟随，无需事件） |
| 对话框关闭时子窗口是否销毁 | 是 |
| 栏内容能否渲染 | 有条件：**先 ShowWindow 再 SetParent** 可以正常渲染；对尚未显示的 WinUI 窗口直接 SetParent 会得到空白条 |
| 是否遮挡对话框控件 | **会**。文件对话框客户区最下面一行是「文件名输入框 + 打开/取消」，任何嵌进客户区底部的栏都必然压住这一行 |
| 尺寸换算 | 子窗口坐标是相对客户区的，还要处理非客户区/DWM 外框差异，横向居中要额外算 |

结论：层级、裁剪、随动天然正确，但与「任何时候不遮挡内容区」直接冲突，放弃。

### 方案 B（采用）：owner 窗口 + 0 间隙贴边 + WinEvent 与常驻轮询随动

做法：

1. `SetWindowLongPtr(栏, GWLP_HWNDPARENT, 对话框)` 建立 owner 关系（不是 SetParent）；
2. 几何：栏**上边缘 = 对话框 DWM 可视外框（`DWMWA_EXTENDED_FRAME_BOUNDS`）的下边，间隙 0**；宽度取可视宽度的一半、水平居中；
   下方工作区放不下时翻到可视上边之上，同样是 0 间隙。1.0.9 及以前这里是 `round(2×缩放)` 的 2–4px 缝，1.0.10 起归零；
3. z 序：栏插到「宿主正上方那个窗口」的**下面**——取 `GetWindow(宿主, GW_HWNDPREV)` 作为 `SetWindowPos` 的 `hWndInsertAfter`，
   因此栏永远紧贴宿主正上方、中间不可能夹第三方窗口；**不使用 `WS_EX_TOPMOST`**，栏不会浮到其它应用之上；
4. `SetWinEventHook`（`WINEVENT_OUTOFCONTEXT`）监听 `EVENT_OBJECT_CREATE/SHOW/HIDE/DESTROY`、`EVENT_OBJECT_LOCATIONCHANGE`、`EVENT_SYSTEM_FOREGROUND/MINIMIZE*`，据此挂栏、随动、销毁；
   另有一条 16ms 设定（实测约 31ms 一拍）的常驻轮询兜底：位置尺寸不变时只读不写，事件被合并或整段丢失时（最小化还原后实测一条事件都不再送达）靠它自愈；
5. 栏窗口加 `WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`，显示/点击都不抢对话框焦点。

为什么这样能同时满足各条约束：

- **同一层、不漂在桌面**：owner 窗口在 z 序上永远只排在 owner 之上，不会漂到其它应用前面；owner 最小化时窗口被系统一并隐藏；
- **多实例天然隔离**：每个对话框各有一个 owner，一条栏只认自己的 owner，`GetWindowLongPtr(-8)` 可逐条核对归属；
- **不遮挡内容**：栏整条都在对话框可视外框之外，客户区不被侵占。代价是 1.0.10 起贴的是可视外框而非「窗口矩形」，
  栏会盖住对话框底边那条 4 物理像素（200%）的不可见缩放热区——底边中段改为拖栏而不是缩放对话框，左右下角仍是对话框的热区；
- **尺寸与 DPI**：宽度取对话框可视宽度的一半。缩放系数按**显示器** DPI 计算，因为被注入的对话框可能来自 DPI 不感知的进程（`GetDpiForWindow` 恒为 96），拿它的返回值算会把栏做成一半大小。

## 非整数缩放（125% / 150%）的核对

本机固定 200%，改 Windows 显示缩放会重排整个桌面并影响正在使用的会话，因此没有真机切缩放，
改用**离屏探针**：`Pathleap.UI.exe --layout-probe=<文件>` 在创建窗口之前调用与运行时**完全相同**的
`QuickSwitchLayout.Attach`（几何计算已抽成纯函数），把本机真实工作区（2880×1704 物理 / 1440×852 DIP）
按 100%、125%、150%、200% 换算成物理像素，再逐项核对半宽、间距、居中、工作区边界、列数阈值。
探针不建窗口、不开管道、不抢前台，写完 JSON 直接退出。

| 缩放 | 常规对话框（720×480 DIP） | 栏 | 窄对话框（280×360 DIP） | 栏 |
| --- | --- | --- | --- | --- |
| 100% | 720×480 | 360×110，间距 2px，偏差 0，3 列 | 280×360 | 140×142，间距 2px，偏差 0，**2 列** |
| 125% | 900×600 | 450×138，间距 2px，偏差 0，3 列 | 350×450 | 175×178，偏差 -0.5px（奇数宽取整），**2 列** |
| 150% | 1080×720 | 540×165，间距 3px，偏差 0，3 列 | 420×540 | 210×213，间距 3px，偏差 0，**2 列** |
| 200% | 1440×960 | 720×220，间距 4px，偏差 0，3 列 | 560×720 | 280×284，间距 4px，偏差 0，**2 列** |

- 半宽：四种缩放下栏宽与对话框可视宽度的差值都 ≤1px；间距按 `round(2×缩放)` 取整（125% 为 2px、150% 为 3px）。
- 列数三档：栏宽 ≥680 DIP 排 6 列；360–680 DIP 排 3 列；<360 DIP 退到 **2 列**（6 个文件夹时 3 行，栏高从 110 涨到 142 DIP，
  仍在 6 行上限内）。阈值取自「3 列时单格文字不足约 70 DIP」：`3×(70+37)+24+10 ≈ 355 DIP`，
  单格固定开销 37 DIP = 左右内边距 14 + 序号徽标 17 + 徽标与文字间距 6。
- 6 列阈值 `680 DIP`：720 DIP 宽的对话框在 125%/150% 下（450/540 DIP 栏宽）仍不足 680，稳定保持 3 列；
  最大化场景（工作区满宽）按 6 列计算。
- 窗口尺寸按 DIP×缩放取整，四种缩放下都是整数像素：主窗 660×436 DIP → 825×545（125%）/ 990×654（150%），
  设置窗 840×640 DIP → 1050×800 / 1260×960，更新窗 440×300 DIP → 550×375 / 660×450。
- 真实 200% 会话复测（本轮重构后）：`dialog=(30,62,1412×946) bar=(383,1026,706×220) scale=2 columns=3`，
  与重构前记录的 706×220 完全一致，说明抽函数没有改变运行时行为。

## 边界场景实测（2026-11-08，200% 缩放）

两个标准「打开」对话框分别由独立进程弹出，用 `SetWindowPos` 摆成互相重叠；栏用
`GetWindow(GW_OWNER) == 对话框` 且进程为 UI 的方式枚举，逐条读 `IsWindowVisible`。

| 场景 | 结果 |
| --- | --- |
| 单个对话框 | 1 条栏，可见 |
| 两个重叠对话框（B 在前台） | A 栏可见性 False，B 栏可见性 True；栏不再压住后方对话框 |
| 切到 A 为前台 | A 栏可见性 True，B 栏可见性 False（只显示前台那条） |
| B 缩窄到平台允许的最小宽度 | 对话框 1250×1400，栏 611×284，宽比 0.49，**2 列 3 行**（长名仍省略，悬停 tooltip 显示完整路径） |
| B 最大化 | 对话框 2848×1672，栏 728,4 1424×156，6 列，整条仍落在工作区内（下方与上方无空间，回退到工作区顶部，只覆盖标题栏） |
| 强杀 A 的进程 | 对话框不存在，栏 total=0（立即随销毁事件移除，无残留） |
| 主动关闭 B | 对话框不存在，栏 total=0 |

> 平台的标准打开对话框存在最小宽度（约 611 DIP），再窄的布局无法用真实对话框构造；
> 280 DIP 的极窄场景由上面的离屏探针覆盖（栏 140–280px、2 列）。

窄对话框的降级形态（2026-11-08 真机）：标准「打开」对话框压到最小宽度后为 1250×1400（物理，625×700 DIP），
栏 611×284（305×142 DIP），自动退到 **2 列 × 3 行**；6 个文件夹里只有超长名（`# Packaging Data 20…`、`temp_20261106_02`）
在格内省略，短名 `docs` / `Downloads` / `Documents` 完整显示。截图
[`docs/shots/28-narrowmin-quickbar.png`](shots/28-narrowmin-quickbar.png)。
对比过的另一种思路是「横向紧凑单行」：栏宽 305 DIP 时 6 格每格仅 45 DIP、文字只剩约 8 DIP，
比 3 列更不可读，因此没有采用；2 列是把同一份数据排得更高的代价换取约 2 倍文字宽度。

## 多显示器与跨屏拖动（2026-11-08）

本机只有一块 200% 显示器（工作区 1440×852 DIP），没有第二块屏，也无法构造不同 DPI 的真实跨屏拖动，
因此仍用离屏探针：`--layout-probe` 增加了合成的三屏拓扑（物理像素、含负坐标），用运行时**同一个**
`QuickSwitchLayout.Attach` 逐屏计算。

| 屏幕 | 有效缩放 | 工作区（物理像素） |
| --- | --- | --- |
| left-150 | 150% | (-2880,-220)–(0,1580) |
| primary-125 | 125% | (0,0)–(2560,1380)（底部留 60px 任务栏） |
| right-100 | 100% | (2560,0)–(4480,1080) |

同一个 720×480 DIP 对话框分别落在三块屏上：

| 屏 | 对话框物理外框 | 栏 | 间距 | 列数 | 落在本屏工作区 |
| --- | --- | --- | --- | --- | --- |
| left-150 | 1080×720 | 540×165 | 3px | 3 | 是 |
| primary-125 | 900×600 | 450×138 | 2px | 3 | 是 |
| right-100 | 720×480 | 360×110 | 2px | 3 | 是 |

跨屏拖动（同一 DIP 尺寸对话框从右屏 → 主屏 → 左屏）每一步都按新屏重算：

- 栏宽依次 360 → 450 → 540px，都等于所在屏对话框物理宽度的一半；
- 每一步的栏都落在该屏工作区内（`allInsideOwnWorkArea=true`），坐标与尺寸逐屏变化
  （`recomputedEveryStep=true`），没有沿用上一屏的位置；
- 间距按各屏缩放取整（2 / 2 / 3px），列数保持 3。

对话框横跨主屏/右屏交界（1125×750 物理像素，约均分两侧）时，`MonitorFromWindow` 只选一块屏，
栏也随之只落在那块屏内并被夹紧（`clampedToChosenMonitor=true`）：

| 系统选中 | 栏 | 结果 |
| --- | --- | --- |
| primary-125 | 562×138 @ (1994,697) | 夹在主屏右边缘，栏与对话框中心的水平偏差约 -285px |
| right-100 | 562×110 @ (2564,696) | 夹在右屏左边缘，偏差约 +285px |

> 跨两屏时栏不会横跨两屏、也不会各画一半；它贴着「对话框所占面积更大的那块屏」的内侧。
> 这是单条栏、单一缩放语义的有意取舍，不是渲染错误。

**运行时可见性（200% 单屏真机复测）**：真实 WinForms 文件夹对话框，栏用
`GetWindow(GW_OWNER) == 对话框` 且进程为 `Pathleap.UI` 枚举，逐次读 `IsWindowVisible`：

| 时点 | 对话框状态 | 栏可见 |
| --- | --- | --- |
| 刚出现 | 前台 | True |
| 程序化最小化（不点击、不激活） | 最小化、非前台 | False |
| `SW_SHOWNOACTIVATE` 还原（前台不变化） | 正常、非前台 | False（+0 / 300 / 1200 / 2500ms 四次采样均为 False） |
| 关闭对话框 | 已销毁 | 栏 total=0 |

这一步暴露并修掉了一个真实缺陷：owner 窗口还原时，系统会把它的附属窗口（栏）一并自动显示，
而旧逻辑只在「栏从隐藏转显示」时重新判断可见性，于是后台对话框还原后栏会重新露出（修复前同样采样四次全为 True）。
现在 `Reposition()` 每次几何事件都按前台状态重套可见性，并订阅 `AppWindow.Changed` 的
`DidVisibilityChange` 兜底：后台状态下一旦被系统显示出来就立即收回。

**未验证**：两块不同 DPI 的真实显示器之间拖动对话框时，WinUI 会收到 `WM_DPICHANGED`，可能按建议矩形
再次重排窗口；本轮只用离屏函数核对了「按新屏重算」的数学分支，没有双 DPI 真机截图。

## `Enter` 真实链路验收（2026-11-08）

两条链路都用真实窗口与真实按键（`SendInput` 合成，非内部调用）：

1. **快速切换栏 → 真实文件夹对话框**
   - 独立进程打开 WinForms 文件夹选择对话框（`#32770`，标题「选择文件夹」），同时开一个指向临时目录
     `lp-enter-target` 的资源管理器窗口，保证栏的第 1 格就是该目录。
   - `Ctrl+G` 让栏进入键盘模式，再按 `Enter`。
   - 日志：`文件对话框注入已发送: kind=选择文件夹 path=C:\…\lp-enter-target edit=0x…`。
   - 用 UIA 读对话框的全部后代 `Name`，在目标目录特有的子目录 `lp-enter-marker-dir` 出现时判定
     「对话框真的进了目标目录」；截图同时显示面包屑 `Temp > lp-enter-target` 与 `文件夹:` 输入框已是该路径。
   - 时序：按键 → 注入发出 **44 ms**；按键 → UIA 看到目标子目录 **272–273 ms**（3 次）。
2. **主搜索窗 → 资源管理器**
   - `QUERY` 选中一个真实目录条目，`SHOW` 后按真实 `Enter`。
   - 结果：资源管理器成为前台窗口（`CabinetWClass`），`LocationURL` 与选中条目路径逐字符一致；
     按键 → 前台化 **749–783 ms**（2 次）。

> 早期 2 次尝试中栏仍处于键盘态但未发生注入，随后 5 次（含还原后的正式构建）全部通过，未能复现；
> 若再次出现，按「低层钩子是否收到按键 / 栏的 `DialogHandle` 与前台句柄是否一致」两处排查。

## 已知限制

1. **只显示前台对话框的栏**：后台对话框的栏隐藏，避免互叠时压住后方内容；代价是必须先激活那个对话框才能看到/点到它的栏。
   多显示器下这一行为相同：即使后台对话框在另一块屏、与前台对话框完全不重叠，它的栏也不显示；栏仍按所在屏的缩放与工作区定位，
   激活后直接出现在正确位置。后台对话框被程序化还原（不激活）时不会把栏带出来（见上一节真机复测）。
2. 对话框被**最大化**时，下方与上方都没有空间，栏会回退到工作区顶部附近（覆盖对话框标题栏而非内容区）。
3. owner 关系是跨进程建立的。若对话框进程被强杀，`EVENT_OBJECT_DESTROY` 通常能收到；为兜底，前台切换时还会检查 owner 是否还存在，不存在就撤栏。
4. 栏宽度严格取对话框可视宽度的一半，因此窄对话框（约 600px 以下）时每格文字会省略显示，悬停 tooltip 显示完整路径。
5. **对话框横跨两块显示器**时，栏只贴在被系统选中（约等于所占面积更大）那块屏的内侧，会因夹紧而不再与对话框水平居中；
   跨屏拖动过程中每次位置变化都会重算，但不同 DPI 下的 `WM_DPICHANGED` 重排未在真机验证。

### 限制

1. **输入态时栏是前台窗口**：要接收键盘就必须成为前台，此时它在 z 序上高于对话框。栏的矩形在对话框外侧（不重叠），
   因此不遮挡任何对话框内容；但这与「任何情况下都不越到对话框之上」的字面要求有出入，属于输入交互的必要代价。
2. **宿主重新激活后栏可能被系统抬到宿主之上**：1.0.9 未完全消除，1.0.10 已修复，见文末。
3. 搜索框的悬停态无像素证据（栏不接收鼠标激活，离屏抓取不到悬停反馈）。
4. `--screen`/`PrintWindow` 在栏隐藏（后台宿主）时抓到的是桌面底色，不能用来判断栏本身的遮挡，这一场景只用
   `IsWindowVisible` 与矩形关系判定。

## 1.0.10 修复：z 序、0 间隙、缩放闪烁与角上白边（2026-11-13）

三条用户反馈一起验：①别的窗口插在栏与对话框之间；②栏要贴着对话框下边缘（此前有 2–4px 缝）；③改尺寸时栏闪烁、四角露白。

- 环境：本机 200% 缩放单屏，工作区 2880×1704 物理像素；
- 采样器：`QsProbeLp.exe`（.NET Framework 独立进程，1ms 级采样），脚本 `tools/Test-LpQuickBarProbe.ps1`；
- 原始输出：修复前 `%TEMP%\pathleap-scaling\qs-probe-base109.txt`（1.0.9 二进制）、修复后 `qs-probe-final4.txt`；
  翻上方核对 `qs-probe-flip.txt`；缩放几何 `scale-gap-check.json`（`--layout-probe` 离屏）；
- 所有 z 序数据都是 `GetWindow(GW_HWNDPREV/NEXT)` 逐条枚举 + `IsWindowVisible` 真实读取，**不是**「代码里调过 `SetWindowPos`」的自证。

### 根因

| 现象 | 根因 |
| --- | --- |
| 第三方窗口插在栏与对话框之间 | 1.0.9 的插入位置是「对话框之后（下面）」，即栏只能保证排在宿主同侧；宿主激活后系统把 owned 窗抬到宿主之上，抬上去的位置不与宿主相邻，再用 150/700ms 两次延后重排去压，中间仍留下窗口 |
| 改尺寸时闪烁 | 1.0.9 每次几何变化都调 `ReorderBelowOwnerDelayed()`：150ms 与 700ms 各一次带 `SWP_SHOWWINDOW` 的 `SetWindowPos`，拖动时每秒几十次重插重绘 |
| 栏不跟随/卡死 | 最小化还原后该对话框不再送 `EVENT_OBJECT_LOCATIONCHANGE`（应用侧一条都没有）；`HideIfShown()` 又停掉跟随计时器，栏永久停在旧位置 |
| 角上白边 | 客户区没有整块填满：`RootGrid` 透明、`RootBorder` 既有 10 DIP 圆角又有自绘描边，圆角把后面的对话框/桌面像素露出来 |
| 2–4px 缝（实测 15px 可视缝） | 贴边基准取 `GetWindowRect` 下边再减 `round(2×缩放)`；`GetWindowRect` 含 DWM 不可见边框（200% 下约 4px），两者叠加成肉眼可见的缝 |

对应改动：

1. 插入位置改为「宿主正上方那个窗口的下面」：`GetWindow(宿主, GW_HWNDPREV)` 作为 `SetWindowPos` 的 `hWndInsertAfter`，
   栏与宿主之间不可能再夹窗口；`SWP_NOZORDER` 的几何移动与 z 序重排彻底分开（同一次调用里参照窗口被销毁会让整次 `SetWindowPos` 失败，栏卡住）。
2. 贴边基准改为 DWM 可视外框（`DWMWA_EXTENDED_FRAME_BOUNDS`）的下边，`GapDip = 0`；翻到上方时同样贴在可视上边，间隙同为 0。
3. 去掉 `ReorderBelowOwnerDelayed()`；改为常驻 16ms（实测约 31ms 一拍）轮询，几何未变时只读不写、不重排 z 序。
4. 客户区整块填满（`RootGrid` 与 `RootBorder` 同色）＋ `RootBorder` 圆角归 0 ＋ DWM 圆角偏好 `DWMWCP_DONOTROUND`。
5. 轮询每拍从 `GetForegroundWindow()` 实时判定前台归属（`GW_OWNER` 逐级上行，不用 root owner），同时负责「还原后重新显示」。

### z 序：同一场景修复前后序列

| 场景 | 1.0.9（base109） | 1.0.10（final4） |
| --- | --- | --- |
| 空闲吸附 | `bar-below between=0`：**栏在对话框下方一层**（首次显示插入位置错误） | `bar-above between=0`；`dialogAboveBarOffset=-1`，`DOWN1=0x3109C8 (#32770)` 即对话框紧邻其下 |
| 点击进入输入态 | `bar-above between=5`：栏虽在之上，但中间夹了 5 个可见窗口 | `bar-above between=0`，`DOWN1=对话框` |
| 点回对话框退出输入态 1.2s 序列 | `badSamples=755249/755249 = 100%`，`final=bar-above:5` | `badSamples=0/743610`，`final=bar-above:0` |
| 点标题栏重新激活 1.5s 序列 | `badSamples=0` 但 `vis=False`（栏已被拖死的逻辑隐藏，采样无效） | `badSamples=0/931737`，`vis=True` |
| 其它程序遮挡后回前台 | 栏 `True→False→True` | 同上，且回来后 `between=0` |
| 最小化 / 还原 | 可见性 `True→False→True`，但还原后栏不再跟随 | `True→False→True`，还原后 `bar-above between=0` |
| 两个对话框切换 | 后台栏未隐藏（另一条栏可见） | 前台那条 `between=0`，后台那条 `visible=False`；关闭后仅剩对应栏 |

采样口径：Z 序列是紧循环逐次读 `GetWindow` 链（1.2s 得 743,610 个样本，平均约 1.6µs 一个），
比它更短的瞬态不会被记录；可见性另有 900ms 点击段的事件级记录（`visChanges`）。
「激活瞬间的短暂窗口」在这两处都没有出现，但**不能据此断言 0 微秒瞬态**。
`[7b] hooktest` 是对照实验：独立进程装同款 `EVENT_OBJECT_LOCATIONCHANGE` 钩子、60Hz 改尺寸 40 帧，
收到 40/40 事件（`perFrame=1.00`），说明「应用侧收不到事件」是实现问题而不是系统不送。

「插入窗口」的直接证据（base109 §4 输入态，从栏往下逐条走 `GW_HWNDNEXT`，`between` 只计可见窗口）：

```
栏 0x200D64 → DOWN1 tooltips_class32 → DOWN2 _SearchEditBoxFakeWindow
            → DOWN3 tooltips_class32 → DOWN4 tooltips_class32 → …（共 5 个可见窗口）
            → 对话框 0x30DA2 (#32770)
紧贴度: bar-above between=5
```

修复后同一场景（final4 §4）栏的正下方第一个就是 `0x3109C8 #32770`，`between=0`，栏与对话框之间没有任何 HWND。
全程 `topmost=False`、`ex=0x8000180`（TOOLWINDOW+NOACTIVATE），**没有用 TOPMOST 绕过**。

### 取舍与副作用（都实测过）

1. **栏改直角**：`DWMWCP_DONOTROUND` + 客户区填满。0 间隙时圆角必然在四角露出后面的像素（不管是对话框阴影还是桌面），
   要「贴死且不露白」就只能不做圆角。代价是与主窗的圆角风格不一致。
2. **对话框底边的不可见缩放热区被盖住**：栏贴在可视下边上，会覆盖对话框窗口矩形底部约 4px（200%）的缩放热区；
   底边中段改为拖动栏，左右下角仍是对话框的热区。这是 0 间隙的直接代价。
3. **轮询节拍 31ms 而非 16ms**：`DispatcherQueueTimer` 在本机实测 31ms 一拍，静止时每拍只做几次窗口查询、不重绘；
   激活/拖动瞬间的滞后由 WinEvent 立即触发的位置计算兜住（实测 3 步延迟 2.77–3.94ms）。
4. **不用 TOPMOST**：探针每轮打印 `topmost=False`；栏始终只是 owned 窗口，其它程序的普通窗口可以正常盖住对话框与栏。
5. **最大化仍不贴边**：对话框最大化时上下都没有空间，栏回退到工作区顶部附近（`gapPx=-848`、`gapMatches=false`），
   与 1.0.9 的既有行为一致，未在本轮改动。
6. **输入态栏仍是前台窗口**：要收键盘就必须成为前台；但采样显示此时它仍紧贴对话框正上方（`between=0`），
   不再越过对话框跑到别的窗口之上。
