# 快速切换栏吸附方案：技术验证与取舍

## 背景

文件对话框打开时，「快速切换栏」需要以附属面板的形态出现：宽度约为对话框的一半、贴在底边、随对话框移动/缩放/最小化，对话框关闭立即消失；多个对话框各有一条、互不串位，只有前台对话框对应的那条响应键盘。

## 候选方案与实测结论

### 方案 A：SetParent 成对话框的子窗口

做法：`SetParent(栏, 对话框)`，再用 `SetWindowPos` 把栏放进对话框客户区底边内侧。

实测结论：

| 项 | 结果 |
| --- | --- |
| 跨进程 SetParent 能否成功 | 能，返回上一个父窗口，无错误 |
| 子窗口是否随对话框移动 | 是（系统原生跟随，无需事件） |
| 对话框关闭时子窗口是否销毁 | 是 |
| 栏内容能否渲染 | 有条件：**先 ShowWindow 再 SetParent** 可以正常渲染；对尚未显示的 WinUI 窗口直接 SetParent 会得到空白条 |
| 是否遮挡对话框控件 | **会**。文件对话框客户区最下面一行是「文件名输入框 + 打开/取消」，任何嵌进客户区底部的栏都必然压住这一行 |
| 尺寸换算 | 子窗口坐标是相对客户区的，还要处理非客户区/DWM 外框差异，横向居中要额外算 |

结论：层级、裁剪、随动天然正确，但与「任何时候不遮挡内容区」直接冲突，放弃。

### 方案 B（采用）：owner 窗口贴在底边外侧 + WinEvent 随动

做法：

1. `SetWindowLongPtr(栏, GWLP_HWNDPARENT, 对话框)` 建立 owner 关系（不是 SetParent）；
2. `SetWindowPos(栏, 对话框, ...)` 放在对话框底边**外侧** 2px，宽度取对话框可视宽度（DWM 扩展外框）的一半，水平居中；
3. `SetWinEventHook`（`WINEVENT_OUTOFCONTEXT`）监听 `EVENT_OBJECT_CREATE/SHOW/HIDE/DESTROY`、`EVENT_OBJECT_LOCATIONCHANGE`、`EVENT_SYSTEM_FOREGROUND/MINIMIZE*`，据此挂栏、随动、销毁；
4. 栏窗口加 `WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`，显示/点击都不抢对话框焦点。

为什么这样能同时满足各条约束：

- **同一层、不漂在桌面**：owner 窗口在 z 序上永远只排在 owner 之上，不会漂到其它应用前面；owner 最小化时窗口被系统一并隐藏；
- **多实例天然隔离**：每个对话框各有一个 owner，一条栏只认自己的 owner，`GetWindowLongPtr(-8)` 可逐条核对归属；
- **不遮挡内容**：栏整条都在对话框窗口矩形之外，客户区不被侵占；贴的是「窗口矩形」底边而不是 DWM 可视外框，避免压住底部拖拽缩放的不可见边框热区；
- **尺寸与 DPI**：宽度取对话框可视宽度的一半。缩放系数按**显示器** DPI 计算，因为被注入的对话框可能来自 DPI 不感知的进程（`GetDpiForWindow` 恒为 96），拿它的返回值算会把栏做成一半大小。

## 边界场景实测（2026-11-08，200% 缩放）

两个标准「打开」对话框分别由独立进程弹出，用 `SetWindowPos` 摆成互相重叠；栏用
`GetWindow(GW_OWNER) == 对话框` 且进程为 UI 的方式枚举，逐条读 `IsWindowVisible`。

| 场景 | 结果 |
| --- | --- |
| 单个对话框 | 1 条栏，可见 |
| 两个重叠对话框（B 在前台） | A 栏可见性 False，B 栏可见性 True；栏不再压住后方对话框 |
| 切到 A 为前台 | A 栏可见性 True，B 栏可见性 False（只显示前台那条） |
| B 缩窄到平台允许的最小宽度 | 对话框 1222×1386，栏 611×220，宽比 0.5，3 列（文字省略，悬停 tooltip 显示完整路径） |
| B 最大化 | 对话框 2848×1672，栏 728,4 1424×156，6 列，整条仍落在工作区内（下方与上方无空间，回退到工作区顶部，只覆盖标题栏） |
| 强杀 A 的进程 | 对话框不存在，栏 total=0（立即随销毁事件移除，无残留） |
| 主动关闭 B | 对话框不存在，栏 total=0 |

> 平台的标准打开对话框存在最小宽度（约 611 DIP），再窄的布局无法用真实对话框构造；
> 280 DIP 的极窄场景由上面的离屏探针覆盖（栏 140–280px、3 列）。

## 多显示器与跨屏拖动（2026-11-08）

本机只有一块 200% 显示器（工作区 1440×852 DIP），没有第二块屏，也无法构造不同 DPI 的真实跨屏拖动，
因此仍用离屏探针：`--layout-probe` 增加了合成的三屏拓扑（物理像素、含负坐标），用运行时**同一个**
`QuickSwitchLayout.Attach` 逐屏计算。

| 屏幕 | 有效缩放 | 工作区（物理像素） |
| --- | --- | --- |
| left-150 | 150% | (-2880,-220)–(0,1580) |
| primary-125 | 125% | (0,0)–(2560,1380)（底部留 60px 任务栏） |
| right-100 | 100% | (2560,0)–(4480,1080) |

同一个 720×480 DIP 对话框分别落在三块屏上：

| 屏 | 对话框物理外框 | 栏 | 间距 | 列数 | 落在本屏工作区 |
| --- | --- | --- | --- | --- | --- |
| left-150 | 1080×720 | 540×165 | 3px | 3 | 是 |
| primary-125 | 900×600 | 450×138 | 2px | 3 | 是 |
| right-100 | 720×480 | 360×110 | 2px | 3 | 是 |

跨屏拖动（同一 DIP 尺寸对话框从右屏 → 主屏 → 左屏）每一步都按新屏重算：

- 栏宽依次 360 → 450 → 540px，都等于所在屏对话框物理宽度的一半；
- 每一步的栏都落在该屏工作区内（`allInsideOwnWorkArea=true`），坐标与尺寸逐屏变化
  （`recomputedEveryStep=true`），没有沿用上一屏的位置；
- 间距按各屏缩放取整（2 / 2 / 3px），列数保持 3。

对话框横跨主屏/右屏交界（1125×750 物理像素，约均分两侧）时，`MonitorFromWindow` 只选一块屏，
栏也随之只落在那块屏内并被夹紧（`clampedToChosenMonitor=true`）：

| 系统选中 | 栏 | 结果 |
| --- | --- | --- |
| primary-125 | 562×138 @ (1994,697) | 夹在主屏右边缘，栏与对话框中心的水平偏差约 -285px |
| right-100 | 562×110 @ (2564,696) | 夹在右屏左边缘，偏差约 +285px |

> 跨两屏时栏不会横跨两屏、也不会各画一半；它贴着「对话框所占面积更大的那块屏」的内侧。
> 这是单条栏、单一缩放语义的有意取舍，不是渲染错误。

**运行时可见性（200% 单屏真机复测）**：真实 WinForms 文件夹对话框，栏用
`GetWindow(GW_OWNER) == 对话框` 且进程为 `Pathleap.UI` 枚举，逐次读 `IsWindowVisible`：

| 时点 | 对话框状态 | 栏可见 |
| --- | --- | --- |
| 刚出现 | 前台 | True |
| 程序化最小化（不点击、不激活） | 最小化、非前台 | False |
| `SW_SHOWNOACTIVATE` 还原（前台不变化） | 正常、非前台 | False（+0 / 300 / 1200 / 2500ms 四次采样均为 False） |
| 关闭对话框 | 已销毁 | 栏 total=0 |

这一步暴露并修掉了一个真实缺陷：owner 窗口还原时，系统会把它的附属窗口（栏）一并自动显示，
而旧逻辑只在「栏从隐藏转显示」时重新判断可见性，于是后台对话框还原后栏会重新露出（修复前同样采样四次全为 True）。
现在 `Reposition()` 每次几何事件都按前台状态重套可见性，并订阅 `AppWindow.Changed` 的
`DidVisibilityChange` 兜底：后台状态下一旦被系统显示出来就立即收回。

**未验证**：两块不同 DPI 的真实显示器之间拖动对话框时，WinUI 会收到 `WM_DPICHANGED`，可能按建议矩形
再次重排窗口；本轮只用离屏函数核对了「按新屏重算」的数学分支，没有双 DPI 真机截图。

## `Enter` 真实链路验收（2026-11-08）

两条链路都用真实窗口与真实按键（`SendInput` 合成，非内部调用）：

1. **快速切换栏 → 真实文件夹对话框**
   - 独立进程打开 WinForms 文件夹选择对话框（`#32770`，标题「选择文件夹」），同时开一个指向临时目录
     `lp-enter-target` 的资源管理器窗口，保证栏的第 1 格就是该目录。
   - `Ctrl+G` 让栏进入键盘模式，再按 `Enter`。
   - 日志：`文件对话框注入已发送: kind=选择文件夹 path=C:\…\lp-enter-target edit=0x…`。
   - 用 UIA 读对话框的全部后代 `Name`，在目标目录特有的子目录 `lp-enter-marker-dir` 出现时判定
     「对话框真的进了目标目录」；截图同时显示面包屑 `Temp > lp-enter-target` 与 `文件夹:` 输入框已是该路径。
   - 时序：按键 → 注入发出 **44 ms**；按键 → UIA 看到目标子目录 **272–273 ms**（3 次）。
2. **主搜索窗 → 资源管理器**
   - `QUERY` 选中一个真实目录条目，`SHOW` 后按真实 `Enter`。
   - 结果：资源管理器成为前台窗口（`CabinetWClass`），`LocationURL` 与选中条目路径逐字符一致；
     按键 → 前台化 **749–783 ms**（2 次）。

> 早期 2 次尝试中栏仍处于键盘态但未发生注入，随后 5 次（含还原后的正式构建）全部通过，未能复现；
> 若再次出现，按「低层钩子是否收到按键 / 栏的 `DialogHandle` 与前台句柄是否一致」两处排查。

## 已知限制

1. **只显示前台对话框的栏**：后台对话框的栏隐藏，避免互叠时压住后方内容；代价是必须先激活那个对话框才能看到/点到它的栏。
   多显示器下这一行为相同：即使后台对话框在另一块屏、与前台对话框完全不重叠，它的栏也不显示；栏仍按所在屏的缩放与工作区定位，
   激活后直接出现在正确位置。后台对话框被程序化还原（不激活）时不会把栏带出来（见上一节真机复测）。
2. 对话框被**最大化**时，下方与上方都没有空间，栏会回退到工作区顶部附近（覆盖对话框标题栏而非内容区）。
3. owner 关系是跨进程建立的。若对话框进程被强杀，`EVENT_OBJECT_DESTROY` 通常能收到；为兜底，前台切换时还会检查 owner 是否还存在，不存在就撤栏。
4. 栏宽度严格取对话框可视宽度的一半，因此窄对话框（约 600px 以下）时每格文字会省略显示，悬停 tooltip 显示完整路径。
5. **对话框横跨两块显示器**时，栏只贴在被系统选中（约等于所占面积更大）那块屏的内侧，会因夹紧而不再与对话框水平居中；
   跨屏拖动过程中每次位置变化都会重算，但不同 DPI 下的 `WM_DPICHANGED` 重排未在真机验证。
