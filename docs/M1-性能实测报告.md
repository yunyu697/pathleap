# M1 唤醒性能实测报告

被测产品：Pathleap / 跃径 `0.1.0-m1`（WinUI 3 / Windows App SDK 2.6.5 / .NET 8）
测试日期：2026-11-06 ~ 2026-11-07

> 注：测量时的构建版本标记为 `0.1.0-m1`；之后版本号机制统一为单一来源，当前版本为 `1.0.0-alpha1`。
> 两者是同一份 M1 骨架代码（除版本号与日志/定位修复外无差异），性能结论不受影响。

结论：**达标，不需要切 Plan B（自绘 overlay）**。

## 1. 结论摘要

方案指标是「按下全局热键 → 可输入」P50 ≤ 45 ms、P95 ≤ 90 ms。Release 构建 1000 次实测：

| 阶段 | P50 | P95 | P99 | 最大值 |
| --- | --- | --- | --- | --- |
| 首帧（CompositionTarget.Rendering 首次回调） | 17.588 ms | 22.787 ms | 26.1 ms | 29.944 ms |
| 输入框获得焦点 | 21.32 ms | 27.606 ms | 31.14 ms | 34.376 ms |
| **可输入（KeyDown 收到探测键）** | **33.673 ms** | **41.739 ms** | **49.559 ms** | **53.608 ms** |
| 文本实际落进 TextBox | 44.864 ms | 56.202 ms | 63.303 ms | 67.754 ms |

- 999 个 warm 样本全部有效送达，0 失败；P95 41.739 ms 距 90 ms 阈值有约 2.2 倍余量，P50 距 45 ms 阈值有约 25% 余量。
- 首帧在 17.6 ms 量级，说明唤醒后第一帧基本落在「下一个刷新周期」内，没有出现上百毫秒的白屏。
- 结论：**WinUI 3 的这条路径能用**。Plan B（Direct2D 自绘 overlay）只有在 P95 接近 90 ms 或首帧 > 1~2 个刷新周期时才需要启动，本次数据不支持切 Plan B。

## 2. 被测机器与运行时

| 项目 | 值 |
| --- | --- |
| CPU | AMD Ryzen 7 7840H with Radeon 780M Graphics，16 逻辑核 |
| OS | Microsoft Windows NT 10.0.26300.0（Windows 11） |
| 显示缩放 | DPI 192（200%） |
| 刷新率 | 系统 API 未返回（`EnumDisplaySettingsW` 报 0，按 60 Hz / 16.7 ms 帧间隔推断） |
| .NET | 8.0.33 |
| UI 框架 | WinUI 3，Microsoft.WindowsAppSDK 2.6.5（unpackaged，`WindowsPackageType=None`） |
| 进程 | UI 进程常驻；索引服务为独立进程（M1 无索引） |

构建：Debug 与 Release 各测一轮，两者都跑 1000 次；另有 Debug 下 200 次的预跑。

## 3. 测量方法（真实路径，不做内部函数计时）

1. **T0**：热键由独立的原生消息线程（`RegisterHotKey` + `WM_HOTKEY`）接收。处理 `WM_HOTKEY` 的第一条指令取 `Stopwatch.GetTimestamp()`（QPC），不经过 UI 线程排队，因此不含「把时间戳算在别的函数里」的误差。
2. **唤醒**：由 `SendInput` 注入真实的 `Ctrl+Alt+Space` 按键序列，走与用户按键完全相同的系统路径；不是直接调用 `ShowWindow`。
3. **首帧**：UI 线程上 `CompositionTarget.Rendering` 的首次回调。
4. **焦点**：搜索框 `GotFocus`。
5. **可输入**：`GotFocus` 后立刻用 `SendInput` 注入探测字符（配置 `benchProbeKey`，默认 `7`），以 UI 线程 `TextBox.KeyDown` 收到该键为准；随后 80 ms 读取 `TextBox.Text` 校验字符真的进入了控件（文本提交时间）。
6. **有效性**：样本必须同时满足「输入已送达 + 焦点已获得 + 窗口在前台 + 窗口可见」，否则记为失败，不进入统计。
7. **冷/热分离**：第 1 个样本单列为冷样本，不计入 warm 分位数（首轮唤醒包含首次图层/交换链初始化）。
8. 分位数用 nearest-rank；每轮之间隐藏窗口等 350 ms，避免上一轮的输入状态串扰。

每轮结果同时写入 `%LOCALAPPDATA%\Pathleap\perf\` 的时间戳 CSV / JSON，以及 `last-bench-summary.json`、`last-bench-samples.csv`。原始数据：`wake-latency-20261107-001527.json`（Release）、`wake-latency-20261107-000508.json`（Debug）、`wake-latency-20261106-235455.json`（Debug 200 次预跑）。

## 4. 结果对比

### Release 1000 次（主结论）

| 指标 | P50 | P95 | P99 | max | min | mean |
| --- | --- | --- | --- | --- | --- | --- |
| 热键 → 调用显示 | 3.925 | 5.573 | 6.376 | 7.556 | 2.033 | 4.01 |
| 热键 → 窗口激活 | 15.747 | 20.674 | 23.377 | 26.075 | 11.533 | 16.203 |
| 热键 → 首帧 | 17.588 | 22.787 | 26.1 | 29.944 | 13.668 | 18.079 |
| 热键 → 焦点 | 21.32 | 27.606 | 31.14 | 34.376 | 16.088 | 21.966 |
| 热键 → 可输入 | 33.673 | 41.739 | 49.559 | 53.608 | 26.098 | 34.541 |
| 热键 → 文本提交 | 44.864 | 56.202 | 63.303 | 67.754 | 35.694 | 45.749 |

分布：可输入 > 45 ms 的样本 38/999（3.8%），> 50 ms 的 7/999（0.7%）；首帧 > 1 个 60 Hz 帧（16.7 ms）的 693/999，> 2 帧（33.4 ms）的 0 个。UI 进程私有工作集约 180.5 MB，私有提交约 96.3 MB。

### Debug 1000 次（对照）

| 指标 | P50 | P95 | P99 | max |
| --- | --- | --- | --- | --- |
| 首帧 | 18.36 | 22.886 | 26.437 | 41.332 |
| 焦点 | 22.273 | 27.687 | 31.388 | 35.473 |
| 可输入 | 34.777 | 44.86 | 51.086 | 58.377 |

可输入 > 45 ms 的样本 48/999（4.8%）。这一轮跑在午夜前后，同机还有 Release 编译、打包、git 操作并行进行，数据略保守。

### Debug 200 次（预跑）

首帧 P50 12.446 / P95 17.866；焦点 P50 16.645 / P95 21.775；可输入 P50 33.26 / P95 40.139（max 101.439，P99 54.431）；文本提交 P50 43.28 / P95 52.103。结论同样是达标，可输入 > 45 ms 的样本 0/199。

Debug 与 Release 的总延迟差异在 1~3 ms 量级，说明瓶颈不在托管代码优化级别，而在窗口显示/合成与输入排队。

## 5. 异常与风险

1. **冷样本失败（每轮的第 1 次唤醒）**：`foregroundOk=false`、`window-not-visible`、焦点超时。两轮 1000 次测试的首个样本都是这个表现，第 2 个样本起恢复正常。
   - 原因判断：进程刚启动时尚未获得前台权限，第一次 `SetForegroundWindow` 被前台锁拒绝；窗口被激活后又立刻失焦，触发「失焦隐藏」而消失。
   - 影响：用户安装/重启后第一次按热键可能失败一次。M1 已加 250 ms 失焦宽限期（避免闪隐），但没有完全消除首次前台锁问题。
   - 建议（M2 做）：唤出后若 120~150 ms 内仍未拿到焦点，主动重试 `Activate()` + `SetForegroundWindow` 一次；或在启动时常驻预热一次前台权限。该改动会改变延迟分布，需连同基准一起重测。
2. **首帧的帧量化**：首帧时间取决于显示刷新周期，P50 17.6 ms 基本等于「下一个 60 Hz 帧」。若目标机是 60 Hz，首帧理论下限约 16.7 ms；高刷屏会更好。本机刷新率 API 返回 0，无法确认，报告按 60 Hz 解释。
3. **P95 在 41.7 ms 仍偏紧**：距离 90 ms 有充足余量，但距离 45 ms 的 P50 阈值只有 ~25%。后续 M2 若在 UI 线程加入真实搜索（哪怕只是本地过滤），必须重跑本基准；建议把「首帧 ≤ 25 ms、可输入 P95 ≤ 60 ms」作为 M2 的内部回归线。
4. **网络/远程会话**：本机 DPI 192、刷新率未知，可能是远程或虚拟显示；若在纯物理 60 Hz 屏上复测，数字可能略有不同。原始数据已带机器信息，便于复现。
5. **基准本身的开销**：每轮隐藏窗口等待 350 ms、注入两次输入，单次约 0.5~0.6 s，1000 次约 8~10 分钟。测试期间其他程序抢焦点会造成失败样本（本轮 Debug 1000 次受并行编译影响，但 warm 失败仍为 0）。

## 6. Plan B 判断

方案里的 Plan B 是「WinUI 3 达不到指标时改用 Direct2D/DirectWrite 自绘 overlay」。基于本次数据：

- 可输入 P95 41.739 ms（Release）优于 90 ms 阈值 2.2 倍，P50 33.673 ms 优于 45 ms 阈值；
- 首帧 17.588 ms，没有出现 > 2 帧的样本；
- 冷启动的首次失败与框架无关，属于前台权限问题，自绘 overlay 同样会遇到。

因此 **不启动 Plan B**。若后续 M2 引入真实搜索与结果列表导致 P95 超过 60 ms，再按方案的 Plan B 评估（预估自绘方案能把首帧压到 1 帧内、总延迟降低 8~12 ms，但需要自己实现文本输入、输入法、无障碍与多屏 DPI，属于 2~3 周量级的替换，不建议在 M2 之前做）。

## 7. 复现方式

```powershell
pwsh -File .\tools\Build-Lp.ps1 -LpConfiguration Release
pwsh -File .\tools\Run-LpBench.ps1 -LpConfiguration Release -LpSamples 1000
```

要求：解锁的交互式桌面、无其它程序占用 `Ctrl+Alt+Space`、测试期间不碰键鼠。结果路径会打印在脚本末尾，原始 CSV 在 `%LOCALAPPDATA%\Pathleap\perf\`。
