# 更新源与签名（公开发布仓库方案）

## 1. 方案与取舍

源码仓库保持私有；另建一个**只放发布产物**的公开仓库 `yunyu697/pathleap-releases`：
安装包、便携包与 `latest.json`，不放源码，因此不需要给客户端任何令牌。

| 方案 | 问题 | 取舍 |
| --- | --- | --- |
| 客户端调私有仓库 `/repos/{owner}/{repo}/releases/latest` | 未认证必 404；给客户端内置 token 等于把凭据发给所有用户 | 放弃 |
| 客户端直接读私有 Release 资产 | 未认证无法下载 | 放弃 |
| **公开发布仓库 + 签名清单（当前）** | 公开仓库任何人都能读清单与资产，必须防篡改 | 采用：Ed25519 签清单 + SHA256 校验资产 |

清单地址固定为：

```
https://github.com/yunyu697/pathleap-releases/releases/latest/download/latest.json
```

`latest.json` 作为「最新正式版 Release」的资产上传，客户端只发普通 GET，**不携带 Authorization、不读任何本地凭据**。
GitHub 的 `/releases/latest` 只指向最新**非预发布** Release，因此预发布版本需要单独的测试通道（未实现）。

## 2. latest.json 字段

```json
{
  "schemaVersion": 1,
  "version": "1.0.5",
  "tag": "v1.0.5",
  "releasedAt": "2026-11-08T00:00:00Z",
  "channel": "stable",
  "platform": "win-x64",
  "minimumSystem": {
    "windows": "10.0.17763.0",
    "dotnetDesktop": "8.0",
    "windowsAppRuntime": "2.6.5"
  },
  "notes": "更新说明……",
  "assets": {
    "installer": {
      "name": "Pathleap-1.0.5-win-x64-setup.exe",
      "size": 8831614,
      "sha256": "<64 位小写十六进制>",
      "url": "https://github.com/yunyu697/pathleap-releases/releases/download/v1.0.5/Pathleap-1.0.5-win-x64-setup.exe"
    },
    "portable": {
      "name": "Pathleap-1.0.5-win-x64.zip",
      "size": 11461968,
      "sha256": "<64 位小写十六进制>",
      "url": "https://github.com/yunyu697/pathleap-releases/releases/download/v1.0.5/Pathleap-1.0.5-win-x64.zip"
    }
  },
  "signature": "<Ed25519 签名，Base64，64 字节>"
}
```

`assets` 顺序固定 `installer` → `portable`；客户端优先选安装包，其次便携包。

## 3. 签名口径（为什么不是「对整个 JSON 签名」）

JSON 排版、字段顺序、转义方式在不同语言间很难逐字节一致，直接签 JSON 很容易出现「发布端签了、客户端验不过」。
因此签名对象是一段**固定格式文本**，由发布工具与客户端共用同一份实现（`LatestManifest.BuildSignedContent()`）：

```
pathleap-manifest-v1
version=1.0.5
tag=v1.0.5
releasedAt=2026-11-08T00:00:00Z
channel=stable
platform=win-x64
minimumSystem.windows=10.0.17763.0
minimumSystem.dotnetDesktop=8.0
minimumSystem.windowsAppRuntime=2.6.5
asset.installer.name=...
asset.installer.size=...
asset.installer.sha256=...
asset.installer.url=...
asset.portable.name=...
asset.portable.size=...
asset.portable.sha256=...
asset.portable.url=...
notes=<多行说明，CRLF 统一为 LF，放在最后>
```

- 只有 `signature` 字段不参与签名；客户端**只使用这些被签名字段**（版本、URL、SHA256、最低系统要求）。
- 签名：Ed25519（RFC 8032），托管实现 `src/Pathleap.Shared/Update/Ed25519.cs`，无第三方依赖；
  自检含 RFC 8032 向量 1/2、随机密钥往返、篡改消息/签名/公钥拒绝。
- 验签失败、公钥缺失、清单缺 `signature`：**直接中止**，不提供「忽略签名继续安装」的开关。
- 下载：先写 `.part`，边下边算 SHA256；大小或哈希不一致就删除 `.part` 并拒绝安装，提示期望值与实际值。

## 4. 凭据（当前策略下不需要 PAT）

### 4.1 PAT：不再需要

2026-11-08 起 GitHub 只打 tag、不发包，CI 不访问任何公开仓库，因此**不需要 `PATHLEAP_RELEASES_PAT`**。
若未来重新开启对外发布，再按「Fine-grained PAT、仅授权公开仓库、`Contents: Read and write`」最小权限原则创建。

### 4.2 签名私钥：固定使用 `release-keys/ed25519-seed.txt`

- 发布私钥**固定**，不再更换。`create` 会把 seed 推导出的公钥与
  [ReleaseSigning.cs](../src/Pathleap.Shared/Update/ReleaseSigning.cs) 的 `PublicKeyBase64` 硬比对：
  不一致（或客户端未内置公钥）**直接失败、不生成清单**；**发版流程不得生成新密钥**。
- `gen-key` 只用于「已明确决定换钥」的场合，**不属于发版步骤**。换钥顺序固定：
  1) 新公钥写进客户端并**先发布**该版本；2) 再用新钥签清单。顺序颠倒会让已装客户端拒绝所有新清单
  （这是预期的「不降级」行为）。
- seed 只存本地 `release-keys/ed25519-seed.txt`（已被 `.gitignore` 覆盖）；
  不提交、不打印、不写进文档或发布说明。给需要的地方赋值时用本地副本
  `release-keys/PATHLEAP_SIGNING_KEY.secret.txt`（内容即 `seedBase64`）。

### 4.3 当前策略：不发布（只打 tag）

- **GitHub 只打 tag 作版本标记**：不创建 Release、不上传任何资产、不跑公开发布步骤。
- 安装包与 zip **只在本地生成**并留在 `dist/`：
  `tools/Package-Lp.ps1`、`tools/Package-LpInstaller.ps1`。
- 请在本地用 `ReleaseTool create` 生成并签名 `dist/latest.json` 留档（`verify` 自检），
  不把清单上传到任何公共位置。
- 因此 `latest.json` 的公开地址当前必然 404，客户端会明确提示「公开发布仓库暂无最新清单（HTTP 404）」，
  自动检查另有托盘提示；这是如实失败，不是静默，也不会谎报有更新。
- 若未来重新决定对外发布，需要另建公开仓库、重新评估凭据与流水线，不应直接恢复旧步骤。

### 4.4 已发布客户端的兼容性（现实约束）

- `1.0.0`–`1.0.4` 的客户端**早于签名机制**：更新检查读的是私有仓库的
  `api.github.com/repos/yunyu697/pathleap/releases/latest`（无令牌，对私有仓库实际返回 404），
  且**没有内置任何公钥**，也无法解析 `latest.json`。
- 因此这些版本**不会自动升级**，必须手动下载并安装首个内置该公钥的版本。
  该版本发布说明中必须写明「旧版本用户需手动升级」，不能声称自动更新可用。

## 5. CI 步骤行为（2026-11-08 起）

`build.yml` 的 tag 触发只做版本标记与校验，**没有任何发布步骤**：

1. 校验 tag 以 `v` 开头、去掉前缀后是合法版本号，注入编译；
2. 脚本变量命名检查；
3. 发布工具 `selftest`；
4. Release 编译（UI / Service / Shared）。

不打包 zip/安装包、不创建 Release、不上传资产；`gh release` 与公开发布步骤已从 workflow 移除。
本地产物用 `tools/Package-Lp.ps1` 与 `tools/Package-LpInstaller.ps1` 生成，清单用 `ReleaseTool create` 本地签名留档。

## 6. 镜像策略

- 更新窗只显示「下载源」状态，不再放下拉：
  - 资产 host 为 `github.com` → 「GitHub 官方直链」；
  - 其它 host → 红色文案「资产不是 github.com 直链（host），镜像不可用」。
- `AppConfig.DownloadMirror` 已删除，旧配置里的该字段会在下次写回时自然消失。

## 7. 本地 dry-run（本轮已验证）

```powershell
# 1) 自检：Ed25519 向量、版本边界、清单签名/篡改
dotnet run --project src/Pathleap.ReleaseTool -- selftest

# 2) 用 dist 里的真实产物生成并签名清单
dotnet run --project src/Pathleap.ReleaseTool -- create `
  --version 1.0.4 --tag v1.0.4 `
  --notes-file docs/1.0.4-发布说明.md `
  --installer dist/Pathleap-1.0.4-win-x64-setup.exe `
  --portable dist/Pathleap-1.0.4-win-x64.zip `
  --out dist/latest.json --seed-file release-keys/ed25519-seed.txt

# 3) 验签
dotnet run --project src/Pathleap.ReleaseTool -- verify --manifest dist/latest.json
```

本轮结果：自检 **22 项全部通过**；清单生成后验签通过；清单 JSON 只含被签名字段
（`schemaVersion` / `version` / `tag` / `releasedAt` / `channel` / `platform` / `minimumSystem` /
`notes` / `assets` / `signature`），计算属性已用 `JsonIgnore` 排除，不再出现 `preferredAsset`、
`hasPortableAsset`、`isUsable`；把 portable 的 SHA256 改一位后验签失败（退出码 1）。
CI 因账户计费阻断未运行，**不声称流水线已跑通**。

### 7.1 本地 HTTPS 回环（数据通路已验证，客户端 UI 未驱动）

- 复用本地既有 seed（`gen-key` 的 `create` 会校验 seed 公钥与内置公钥一致，不一致直接报错；本次生成成功即证明两者一致，无需换钥、无需为新钥重发版）。
- 用 1.0.4 真实产物生成一份指向 `https://localhost:8791/...` 的测试清单（URL 在签名范围内，`verify` 通过），
  用自签证书的本地静态服务提供清单与两个资产。
- 拉取 `latest.json` → 验签通过；按清单中的 URL 下载 setup：大小 `8,831,614` 与 SHA256 均与清单一致。
- 把服务器上的资产翻转一字节再下载：大小相同、SHA256 不一致——客户端据此删除 `.part` 并拒绝安装。
- **未验证（已被 7.2 覆盖）**：没有驱动 WinUI 客户端本体。`UpdateService` 的清单地址是编译期常量；
  本地用 `-SkipCertificateCheck` 跳过自签证书（真实 GitHub 走受信任证书链），真实 TLS 下的 404 见 7.2。
  seed 只落在 `release-keys/`（已被 `.gitignore` 覆盖），未出现在工作区、历史提交与 docs 中。

### 7.2 无 Release 时的真实 404（2026-11-08 实测）

- 直接访问清单地址得到 **HTTP 404**（仓库 `yunyu697/pathleap-releases` 不存在，也没有任何 Release）。
- 把本地配置的 `lastUpdateCheck` 置为过期后启动 `Pathleap.UI.exe --tray`，自动检查路径实际执行，
  日志实测（10:19:31）：
  `更新检查失败: 公开发布仓库暂无最新清单（HTTP 404）：https://github.com/.../latest.json`
- 界面表现：手动点「检查更新」→ 窗内红字「检查失败：公开发布仓库暂无最新清单（HTTP 404）…」；
  自动检查现在写「自动检查更新未完成: <原因>」并调用托盘提示（本轮新增）——托盘气泡未截图验证；
  两种路径都**不会**显示「有新版本」。
- 复跑时 GitHub 连接出现 `SSL connection could not be established`，未再次取到 404 样本；
  404 判定本身已由 HTTP 状态与上面的日志确认，客户端把网络错误同样按失败上报告知，不会当成「已是最新」。
- 测试后已还原 `config.json`，并 `--quit` 结束测试实例。

## 8. 已知限制

- 当前 GitHub 不承载任何发布资产（只打 tag），因此清单地址始终 404；这不是缺陷，是既定策略下的如实失败。
- `/releases/latest` 只指向最新非预发布版；预发布通道未实现。
- 清单与资产都从 GitHub 下载；没有自建镜像源，因此不提供镜像切换。
- 客户端只校验清单签名与资产 SHA256，不校验安装包内的签名证书（Inno Setup 未签名）。
- 公钥轮换需要发新版本；旧版本客户端会拒绝新密钥签名的清单（这是预期的「不降级」行为）。
