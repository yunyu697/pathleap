# 更新源与签名（公开主仓库方案）

## 1. 方案与取舍

源码仓库 `yunyu697/pathleap` 已**公开**，Release 直接发在主仓库上，不再需要单独的发布仓库。
客户端只读该仓库最新 Release 的 `latest.json` 与资产，**零令牌**。

| 方案 | 问题 | 取舍 |
| --- | --- | --- |
| 客户端调私有仓库 `/repos/{owner}/{repo}/releases/latest` | 未认证必 404；给客户端内置 token 等于把凭据发给所有用户 | 放弃 |
| 客户端直接读私有 Release 资产 | 未认证无法下载 | 放弃 |
| 单独的公开产物仓库（历史方案 `pathleap-releases`） | 多一个仓库要维护，更新源与源码脱节 | 放弃（仓库已公开） |
| **公开主仓库 + 同一仓库 Release + 签名清单（当前）** | 公开仓库任何人都能读清单与资产，必须防篡改 | 采用：Ed25519 签清单 + SHA256 校验资产 |

清单地址固定为：

```
https://github.com/yunyu697/pathleap/releases/latest/download/latest.json
```

`latest.json`（以及分离签名 `latest.json.sig`）由 tag 流水线作为 Release 资产上传；客户端只发普通 GET，
**不携带 Authorization、不读任何本地凭据**。

GitHub 的 `/releases/latest` 只指向最新**非预发布** Release，因此预发布版本需要单独的测试通道（未实现）。

## 2. latest.json 字段

```json
{
  "schemaVersion": 1,
  "version": "1.0.5",
  "tag": "v1.0.5",
  "releasedAt": "2026-11-08T00:00:00Z",
  "channel": "stable",
  "platform": "win-x64",
  "minimumSystem": {
    "windows": "10.0.17763.0",
    "dotnetDesktop": "8.0",
    "windowsAppRuntime": "2.6.5"
  },
  "notes": "更新说明……",
  "assets": {
    "installer": {
      "name": "Pathleap-1.0.5-win-x64-setup.exe",
      "size": 8831614,
      "sha256": "<64 位小写十六进制>",
      "url": "https://github.com/yunyu697/pathleap/releases/download/v1.0.5/Pathleap-1.0.5-win-x64-setup.exe"
    },
    "portable": {
      "name": "Pathleap-1.0.5-win-x64.zip",
      "size": 11461968,
      "sha256": "<64 位小写十六进制>",
      "url": "https://github.com/yunyu697/pathleap/releases/download/v1.0.5/Pathleap-1.0.5-win-x64.zip"
    }
  },
  "signature": "<Ed25519 签名，Base64，64 字节>"
}
```

`assets` 顺序固定 `installer` → `portable`；客户端优先选安装包，其次便携包。

## 3. 签名口径（为什么不是「对整个 JSON 签名」）

JSON 排版、字段顺序、转义方式在不同语言间很难逐字节一致，直接签 JSON 很容易出现「发布端签了、客户端验不过」。
因此签名对象是一段**固定格式文本**，由发布工具与客户端共用同一份实现（`LatestManifest.BuildSignedContent()`）：

```
pathleap-manifest-v1
version=1.0.5
tag=v1.0.5
releasedAt=2026-11-08T00:00:00Z
channel=stable
platform=win-x64
minimumSystem.windows=10.0.17763.0
minimumSystem.dotnetDesktop=8.0
minimumSystem.windowsAppRuntime=2.6.5
asset.installer.name=...
asset.installer.size=...
asset.installer.sha256=...
asset.installer.url=...
asset.portable.name=...
asset.portable.size=...
asset.portable.sha256=...
asset.portable.url=...
notes=<多行说明，CRLF 统一为 LF，放在最后>
```

- 只有 `signature` 字段不参与签名；客户端**只使用这些被签名字段**（版本、URL、SHA256、最低系统要求）。
- 签名：Ed25519（RFC 8032），托管实现 `src/Pathleap.Shared/Update/Ed25519.cs`，无第三方依赖；
  自检含 RFC 8032 向量 1/2、随机密钥往返、篡改消息/签名/公钥拒绝。
- 验签失败、公钥缺失、清单缺 `signature`：**直接中止**，不提供「忽略签名继续安装」的开关。
- 下载：先写 `.part`，边下边算 SHA256；大小或哈希不一致就删除 `.part` 并拒绝安装，提示期望值与实际值。
- `latest.json.sig` 是同一签名的分离副本（内容为 Base64 签名一行），供人工核对与第三方校验；客户端验签使用清单内字段。

## 4. 凭据

### 4.1 不需要 PAT

仓库公开 + 同一仓库发布，CI 只用仓库自带的 `GITHUB_TOKEN`（`permissions: contents: write`），
客户端零令牌。**不再需要 `PATHLEAP_RELEASES_PAT`**，也不再需要任何针对发布仓库的细粒度令牌。

### 4.2 签名私钥：固定使用 `release-keys/ed25519-seed.txt`

- 发布私钥**固定**，不再更换。`create` 会把 seed 推导出的公钥与
  [ReleaseSigning.cs](../src/Pathleap.Shared/Update/ReleaseSigning.cs) 的 `PublicKeyBase64` 硬比对：
  不一致（或客户端未内置公钥）**直接失败、不生成清单**；**发版流程不得生成新密钥**。
- `gen-key` 只用于「已明确决定换钥」的场合，**不属于发版步骤**。换钥顺序固定：
  1) 新公钥写进客户端并**先发布**该版本；2) 再用新钥签清单。顺序颠倒会让已装客户端拒绝所有新清单
  （这是预期的「不降级」行为）。
- seed 只存本地 `release-keys/ed25519-seed.txt`（已被 `.gitignore` 覆盖）；
  不提交、不打印、不写进文档或发布说明。CI 签名时从仓库 secret `PATHLEAP_SIGNING_KEY` 读取。

### 4.3 CI 缺 secret 时的行为

- `PATHLEAP_SIGNING_KEY` 未配置或为空：zip/安装包照常上传；随后 `Write-Warning` 并在 workflow 注解里
  输出 `::warning title=本次未生成清单::…`，**不生成也不上传未签名的 `latest.json`**。
- 该步骤以 0 退出（产物可用、清单缺失是已知状态），但日志与注解必须能看到；不允许静默通过。

### 4.4 已发布客户端的兼容性（现实约束）

- `1.0.0`–`1.0.4` 的客户端**早于签名机制**：更新检查读的是私有仓库时期的旧地址（无令牌对私有仓库实际返回 404），
  且**没有内置任何公钥**，也无法解析 `latest.json`。
- 因此这些版本**不会自动升级**，必须手动下载并安装首个内置该公钥的版本。
  该版本发布说明中必须写明「旧版本用户需手动升级」，不能声称自动更新可用。

## 5. CI 步骤行为

`build.yml` 的 tag `v*` 触发执行完整链路：

1. 校验 tag 以 `v` 开头、去掉前缀后是合法版本号，注入编译；
2. 脚本变量命名检查；
3. 发布工具 `selftest`；
4. Release 编译（UI / Service / Shared）；
5. 打包 zip 与安装包（`tools/Package-Lp.ps1`、`tools/Package-LpInstaller.ps1`）；
6. 产物完整性核对：zip 必须包含 `runtimes\win-x64\native\Microsoft.WindowsAppRuntime.Bootstrap.dll`；
7. 创建/更新该 tag 的 Release，上传 zip、安装包；
8. 有 `PATHLEAP_SIGNING_KEY`：把 seed 写入临时文件 → `ReleaseTool create --sig-out` → `verify` →
   上传 `latest.json` 与 `latest.json.sig`（seed 公钥与内置公钥不一致时流水线失败，不产出清单）。

main / PR 只做 1–4（校验与编译），不打包、不发布。本机用 `tools/Package-Lp*.ps1` 可产出等价产物作为备用路径。

## 6. 镜像策略

- 更新窗只显示「下载源」状态，不再放下拉：
  - 资产 host 为 `github.com` → 「GitHub 官方直链」；
  - 其它 host → 红色文案「资产不是 github.com 直链（host），镜像不可用」。
- `AppConfig.DownloadMirror` 已删除，旧配置里的该字段会在下次写回时自然消失。

## 7. 本地 dry-run（已验证）

```powershell
# 1) 自检：Ed25519 向量、版本边界、清单签名/篡改
dotnet run --project src/Pathleap.ReleaseTool -- selftest

# 2) 用 dist 里的真实产物生成并签名清单（同时写出分离签名）
dotnet run --project src/Pathleap.ReleaseTool -- create `
  --version 1.0.4 --tag v1.0.4 `
  --notes-file docs/1.0.4-发布说明.md `
  --installer dist/Pathleap-1.0.4-win-x64-setup.exe `
  --portable dist/Pathleap-1.0.4-win-x64.zip `
  --out dist/latest.json --sig-out dist/latest.json.sig `
  --seed-file release-keys/ed25519-seed.txt

# 3) 验签
dotnet run --project src/Pathleap.ReleaseTool -- verify --manifest dist/latest.json
```

本轮结果：自检 **22 项全部通过**；清单生成后验签通过；清单 JSON 只含被签名字段
（`schemaVersion` / `version` / `tag` / `releasedAt` / `channel` / `platform` / `minimumSystem` /
`notes` / `assets` / `signature`），计算属性已用 `JsonIgnore` 排除；把 portable 的 SHA256 改一位后验签失败（退出码 1）。

### 7.1 本地 HTTPS 回环（数据通路已验证）

- 用 1.0.4 真实产物生成一份指向 `https://localhost:8791/...` 的测试清单（URL 在签名范围内，`verify` 通过），
  用自签证书的本地静态服务提供清单与两个资产。
- 拉取 `latest.json` → 验签通过；按清单中的 URL 下载 setup：大小 `8,831,614` 与 SHA256 均与清单一致。
- 把服务器上的资产翻转一字节再下载：大小相同、SHA256 不一致——客户端据此删除 `.part` 并拒绝安装。
- 本地用 `-SkipCertificateCheck` 跳过自签证书（真实 GitHub 走受信任证书链）。

### 7.2 清单缺失时的真实 404（2026-11-08 实测）

- 仓库公开前 / 清单上传前，直接访问清单地址得到 **HTTP 404**。
- 把本地配置的 `lastUpdateCheck` 置为过期后启动 `Pathleap.UI.exe --tray`，自动检查路径实际执行，
  日志实测（10:19:31）：
  `更新检查失败: 主仓库暂无最新清单（HTTP 404）：https://github.com/.../latest.json`
- 界面表现：手动点「检查更新」→ 窗内红字「检查失败：主仓库暂无最新清单（HTTP 404）…」；
  自动检查写 WARN 日志并调用托盘提示——两种路径都**不会**显示「有新版本」。
- 复跑时 GitHub 连接出现 `SSL connection could not be established`，未再次取到 404 样本；
  404 判定本身已由 HTTP 状态与上面的日志确认，客户端把网络错误同样按失败上报告知，不会当成「已是最新」。

### 7.3 真实 Release 与整链实测（2026-11-08）

计费恢复后重跑 tag 的 run `42365475408`（`success`），`v1.0.4` Release 已创建，四项资产齐备：
`Pathleap-1.0.4-win-x64.zip` 11,462,901 字节、`-setup.exe` 8,795,197 字节、`latest.json` 21,454 字节、
`latest.json.sig` 90 字节。

1. **真实清单可达（零令牌）**：直接 GET
   `https://github.com/yunyu697/pathleap/releases/latest/download/latest.json` → `HTTP 200`、21,454 字节，
   `version=1.0.4`、`tag=v1.0.4`，安装包 URL 指向 `.../releases/download/v1.0.4/...`；
   `latest.json.sig` 同样 `HTTP 200`。
2. **真实客户端检查（用真实 Release 作源）**：用当前 HEAD 构建 `Pathleap.UI.exe --tray`，
   把 `lastUpdateCheck` 置为过期以触发自动检查，日志实测：
   `更新检查完成: remote=1.0.4 local=1.0.4 update=False asset=Pathleap-1.0.4-win-x64-setup.exe signature=ok`，
   随后 `自动检查更新: 清单已验签 · 最低 Windows 10.0.17763.0`。即真实网络下清单拉取 + Ed25519 验签通过；
   因本地就是 1.0.4，判定「无更新」符合预期。
3. **「发现新版本 → 下载 → SHA256」整链（本地清单作源，资产仍取自真实 Release）**：
   本机临时把清单地址指向 `http://127.0.0.1:8791/latest.json`（仅测试构建，测完已还原），
   用固定私钥签一份 `version=1.0.5` 的清单，资产 URL 指向真实 `v1.0.4` Release；
   用客户端同一份 `UpdateService` 代码驱动（临时控制台工程，未提交）：
   - `check ok=True hasUpdate=True remote=1.0.5 signature=True asset=Pathleap-1.0.4-win-x64-setup.exe`；
   - 下载 8,795,197 字节，`sha256=6f60f3c5…c30ad` 与清单期望值一致，退出码 0。
4. **校验失败会拒绝（同一路径的负向验证）**：把清单里的安装包哈希改成篡改副本的值（清单照样签名有效），
   客户端下载真实资产后报告
   `安装包校验失败（大小 8795197/8795197，SHA256 6f60f3c5…，期望 164141…），已删除下载文件并拒绝安装。`
   说明「签名有效 ≠ 资产可信」，SHA256 绑定仍独立生效。

> 溯源说明：第 2 项是**真实 Release**；第 3、4 项清单来自本地回环，资产来自真实 Release。
> 测试用的临时控制台工程与本地清单已删除，产品代码里的清单地址已恢复为主仓库地址。

## 8. 已知限制

- `/releases/latest` 只指向最新非预发布版；预发布通道未实现。
- 清单与资产都从 GitHub 下载；没有自建镜像源，因此不提供镜像切换。
- 客户端只校验清单签名与资产 SHA256，不校验安装包内的签名证书（Inno Setup 未签名）。
- 公钥轮换需要发新版本；旧版本客户端会拒绝新密钥签名的清单（这是预期的「不降级」行为）。
- `1.0.1`–`1.0.3` 的 Release 只有 zip 与安装包，没有 `latest.json`；清单机制自 1.0.4 起生效。
